# Working on Turbofan

Turbofan: a Raft-replicated state machine framework in Rust, and an OMS built on it.
The house style is [docs/STYLE.md](docs/STYLE.md) (Tiger Style, adapted from Turbojet's): read it
before writing code.

- `crates/turbofan-cluster` is the reusable core. It must never depend on a service or mention
  what one does: service payloads are opaque bytes. `raft/` replicates opaque records and knows nothing of
  sessions or services; `node/` layers those on top.
- The core is sans-IO: inputs in, outputs out, no IO, no clock reads. The driver and the
  simulator do the IO.
- The wire protocol is `crates/turbofan-cluster/schema/cluster.xml`, generated by `build.rs` with
  `crates/turbofan-sbe` (SBE codegen and runtime, copied from Turbojet). Change the schema, not the
  generated code, and only as `docs/WIRE.md` allows: old and new nodes run side
  by side. A generator change: `SBE_REGENERATE=1 cargo test -p turbofan-sbe` rewrites its
  checked-in test codecs.
- Services live in repositories of their own, depending on it by git (or crates.io): the OMS (an order book) is
  at `../oms`. A framework change can break one: check it there with `cargo update -p
  turbofan-cluster` and its `scripts/check.sh`.
- `scripts/check.sh` (fmt, clippy `-D warnings`, tests, rustdoc, `cargo deny`) before calling work
  done.
  `cargo bench -p turbofan-cluster --bench cluster` for throughput and latency (`--features tls`
  adds runs over TLS) (CI's summary has
  each run's).
  `SIM_SEEDS=1000 cargo test -p turbofan-cluster --release --test sim` for a longer simulation; a failure
  prints `SIM_SEED=<n>`, which replays it.
- `scripts/site.sh [--serve]` builds the website into `target/site` (mdbook, mdbook-mermaid): the
  landing page `site/index.html`, and the cluster's guide and ARCHITECTURE.md as a book, assembled
  by `site/build.py`, which fails the build if what it reads from the docs moves.
- `scripts/mutants.sh [base]` (cargo-mutants) mutation-tests the Rust changed since `base` (the commit
  before `HEAD` by default): a mutant the tests miss is code they don't check. CI runs it on each push
  and pull request, a missed mutant a warning on its line.
- `scripts/fuzz.sh` fuzzes what the cluster reads from the network (`crates/turbofan-cluster/fuzz`,
  outside the workspace; nightly and cargo-fuzz). `check.sh` only checks it builds.
- Releasing: both crates share the workspace version. Bump it (and `cargo update -w` both lock files, the
  fuzz crate's too), date its `CHANGELOG.md` section, write its golden files (`GOLDEN_WRITE=1 cargo
  test -p turbofan-cluster --test golden`, checked in under `tests/golden/<version>/`),
  `cargo publish --workspace` (the user runs it: their token), then `scripts/github-release.sh <version>`
  tags `v<version>` and makes the GitHub release from that section. Pushing the tag also
  deploys the website (`.github/workflows/site.yml`), built from the tag's docs.
- CI runs the simulation's fixed seeds and the fuzz targets' build in jobs of their own on every push;
  fresh seeds and a ten-minute soak of busy clients through failovers and partitions (`simulate.yml`; `SOAK_SECS=600
  cargo test -p turbofan-cluster --release --test soak` locally) and fuzzing
  (`fuzz.yml`) run nightly, and a failing night opens an issue (`scripts/nightly-report.sh`).
  `scripts/nightly.sh [run]` shows how they went, and fetches a failed one's seed or inputs and
  prints the commands that replay it.
